## DP-020 — Mutable advancing fixture mistaken for a stage-bound control schedule

- Severity: Critical when mutation evidence supports lifecycle, migration,
  research integrity, recovery, deployability, phase acceptance, or authority.
- Status: CONTAINED/BLOCKED. The staged-lifecycle owner froze nine blocked
  outputs after its initial attempt and only repair failed on two distinct
  control-scheduling defects. The candidate source and schema bytes are
  immutable diagnostic input only. No independent reviewer or actual package
  owner started. Product, tests, PostgreSQL, migration, runtime, deployment,
  production, live, order, and money bytes remain unchanged.
- Incident: the initial staged owner attempt changed a static receipt while
  testing interpreter/substrate drift. The exact earlier restoration guard
  correctly returned `RESTORATION_RECEIPT_MISMATCH` before the intended
  `EXECUTION_SUBSTRATE_DRIFT`. The sole repair moved the target to a case-stage
  receipt and proved its scope. The repaired run then advanced one mutable
  fixture to the 19-member mutation stage and invoked a portable selected-subset
  control as `CASES_COMPLETE`. The exact stage-topology guard correctly returned
  `PACKAGE_TOPOLOGY_MISMATCH` before the intended
  `PORTABLE_IDENTITY_INCOMPLETE`. Four modes, all 22 cases, all 28 mutations,
  all eight historical diagnostic sets, and the real race passed, but the two
  remaining modes, both relocation roots, portable controls, execution-fact
  negatives, global identities, and other mandatory checks never ran.
- Root cause: the control runner shared one advancing mutable fixture across
  controls and selected each control's stage and target at execution time. It
  did not freeze a control schedule that bound control ID, exact immutable input
  stage, member-set hash, target membership, guard precedence, expected
  diagnostic, restoration scope, and post-control positive check before the
  attempt began.
- Violated invariant: every Critical control must execute from a fresh immutable
  copy of its exact declared predecessor stage. A preflight must prove that the
  mutation target exists in that stage, is outside earlier authority or
  restoration guards unless those guards are the expected result, and reaches
  the intended first applicable guard. A control run against the wrong stage is
  a scheduler defect, not evidence for or against the validator.
- Why prior evidence missed it: syntax, hash-DAG, and early positive modes did
  not exercise control order. The runner's builder encoded stage progression as
  mutable object state, while the matrix described controls as if each owned an
  independent stage snapshot. Aggregate 22/28/8 counts hid the unexecuted
  portable, relocation, sealed, root-read-only, and attribution gates.
- False assumption: a deterministic runner can advance one fixture once and
  later ask an earlier-stage question by changing only the stage argument.
- Permanent regressions: (1) freeze a root-owned schedule row for every control
  with exact stage, member-set hash, target, expected first guard, expected
  diagnostic, restoration boundary, and post-control positive check; (2) reject
  a static target used for a case-stage execution-substrate control before
  validator invocation; (3) reject a 19-member mutation snapshot presented as
  `CASES_COMPLETE` before validator invocation; (4) start every control from a
  new copy of the exact stage snapshot; (5) execute canonical, reverse, and
  deterministic shuffled schedules twice and require identical results and
  restoration; (6) rehash frozen candidate source, schema, authority, and stage
  snapshots before and after every run; (7) complete all six modes and two
  relocation roots; and (8) require the full unexecuted DP-019, portable,
  execution-fact, global-identity, filesystem, seal, and fresh-positive matrix.
- Adversarial generalization: search migration fixtures, transaction tests,
  retry/recovery suites, provider simulations, concurrent resource tests,
  research replays, and deployment rehearsals for one mutable state reused
  across controls that claim independent starting conditions. Ask whether a
  valid earlier guard masks the named guard and whether order changes outcomes.
- Transitive evidence map: root-frozen control schedule -> immutable exact-stage
  snapshots -> order-independent external execution -> staged grammar evidence
  -> actual JSON-only package -> PostgreSQL and migration evidence -> foundation
  closure -> Phase 5 and Phase 6 handoff. Every downstream claim remains blocked.
- Owner: a fresh staged-lifecycle evidence-orchestration recovery capsule must
  keep the nine blocked candidate outputs read-only. Root first owns and freezes
  the schedule and orchestrator. A fresh evidence runner may execute only those
  bytes and write disjoint evidence, followed by root reproduction and one

## DP-021 — Expected arrays and receipt roles mistaken for executed semantic evidence

- Severity: Critical when receipts support migration, research integrity,
  recovery, deployability, phase acceptance, or authority.
- Status: CONTAINED/BLOCKED. Root rejected the staged orchestration capsule
  before implementation after proving that its immutable candidate has no case
  or mutation execution seam. None of the four planned root orchestration
  outputs exists, no child started, and no root attempt or repair was spent.
  Product, tests, PostgreSQL, migration, runtime, deployment, production, live,
  order, and money bytes remain unchanged.
- Incident: the candidate declared 22 case receipts and 28 mutation receipts,
  but its package stored the root expected case array and mutation
  ID/diagnostic array as outcome matrices. Its receipt schema recorded role,
  process facts, return code, stdout hash, and stderr hash, but no observed case
  disposition, violation-code array, mutation diagnostic, or material before and
  after state. Every case and mutation receipt invoked the same stage validator.
  The two-file executable universe contained only that stage validator and the
  changed-after-read driver. The stage validator compared copied arrays to root
  expectations and never parsed completed stdout for semantic results. The race
  driver implemented only `closure::changed_after_read_member`. No executable
  could perform `legal_full_reseal`, `cycle`, `multi_parent_loss`, the other
  cases, or the 27 non-race mutations.
- Root cause: the architecture separated external process receipts from package
  data but treated a role label plus stream hashes as proof that the named
  semantic operation ran. It froze expected results inside candidate matrices
  without freezing an executable that could derive observed results from
  accepted material authority. The proposed root orchestrator could sequence
  processes, but satisfying the missing behavior would require it to implement
  graph, closure, mutation, and grading logic and become an undeclared second
  semantic oracle.
- Violated invariant: every named semantic receipt must bind a completed process
  whose frozen executable actually implements that exact operation against
  byte-exact accepted material inputs. The receipt must carry independently
  observable disposition, violation or diagnostic arrays, material before and
  after digests, and restoration facts. A package matrix must be derived from
  completed receipt bytes; copying expected authority into an outcome field is
  not observation.
- Why prior evidence missed it: earlier work counted receipt roles, checked
  external hashes, and mutated copied outcome arrays. It proved package shape,
  attribution, and guard behavior around those arrays, not the graph semantics
  named by the roles. The staged owner harness also graded its own controls, so
  the absence of a candidate semantic executor was hidden behind passing 22/28
  counts.
- False assumption: a receipt named `case:cycle` proves the cycle case ran when
  its recorded process was only a generic stage validator and its outcome was
  copied from root authority.
- Permanent regressions: (1) enumerate the complete executable operation set and
  require one closed operation for every case, mutation, historical replay,
  stage mode, relocation, and root recomputation; (2) reject any receipt whose
  executable role cannot perform its named operation; (3) reject an outcome
  matrix equal to expected authority when no completed observed receipts exist;
  (4) require exact observed dispositions and violation or diagnostic arrays in
  every receipt; (5) bind material before and after digests plus restoration;
  (6) alter one executor operation while preserving receipt labels and hashes,
  then require independent failure; (7) omit accepted graph, closure, universe,
  or mutation-restoration material and reject before execution; (8) prove the
  orchestrator contains no semantic grading logic; and (9) repeat execution in
  different schedules while deriving identical matrices from receipts.
- Adversarial generalization: search admission receipts, migration logs,
  provider capability evidence, transaction/retry tests, deployment preflights,
  backup reports, and money reconciliation for role names or expected arrays
  presented as proof that the named producer executed and observed the result.
- Transitive evidence map: root-frozen material semantic executor -> completed
  observed receipts -> non-grading orchestration -> staged package evidence ->
  actual JSON-only package -> PostgreSQL and migration evidence -> foundation
  closure -> Phase 5 and Phase 6 handoff. Every downstream claim remains blocked.
- Owner: a fresh unified semantic-and-stage executor architecture capsule must
  replace the frozen candidate source universe. Root first freezes exact
  material input paths and hashes plus operation and receipt contracts. One
  fresh owner may implement a single self-contained unified executor and one
  race driver, followed by root reconstruction and independent review.
